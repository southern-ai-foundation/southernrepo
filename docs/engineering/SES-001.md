# SES-001: Southern Engineering Standard

**Status:** Founding Draft  
**Version:** 0.1  
**Project:** Southern  
**Founder:** Manish Mathew  
**Established:** 2026-08-02  

## 1. Purpose

This specification defines the minimum engineering, security, quality and governance requirements for all Southern software, model, dataset and research repositories.

Southern is developed openly, but no contributor, maintainer or AI agent may bypass these standards.

## 2. Core engineering principles

Southern engineering must be:

- Open and reproducible
- Secure by design
- Privacy preserving
- Model neutral
- Licence aware
- Test driven
- Reviewable and auditable
- Accessible to outside contributors
- Respectful of cultural authority
- Independent from any single AI provider

## 3. Authority

The Southern project is currently under founding governance.

Final authority during the founding stage rests with:

**Manish Mathew — Founder**

Technical authority may later be delegated through documented maintainer and steering structures.

No AI system has governance, ownership, publication or merge authority.

## 4. Repository requirements

Every production repository must include:

- `README.md`
- `LICENSE`
- `NOTICE`
- `SECURITY.md`
- `CONTRIBUTING.md`
- `CODE_OF_CONDUCT.md`
- `ROADMAP.md`
- `CHANGELOG.md`
- `.gitignore`
- `.github/CODEOWNERS`
- Pull request template
- Issue templates
- Automated tests
- Dependency and secret scanning

## 5. Branch strategy

The protected production branch is:

`main`

Direct development on `main` is prohibited.

Approved branch prefixes:

- `feature/`
- `fix/`
- `docs/`
- `security/`
- `research/`
- `benchmark/`
- `model/`
- `data/`
- `release/`

Examples:

- `feature/model-router`
- `security/input-validation`
- `benchmark/australian-english-v01`
- `docs/data-governance-update`

## 6. Pull request requirements

Every change must be submitted through a pull request.

Each pull request must include:

- Purpose of the change
- Related issue
- Testing completed
- Security impact
- Privacy impact
- Licence and provenance review
- Documentation changes
- Known limitations
- Rollback considerations where relevant

A contributor must not approve their own work as the only reviewer once additional maintainers are available.

## 7. AI-generated contributions

Southern may use Kimi, Qwen, DeepSeek, Southern models and other approved AI systems to assist development.

AI agents may:

- Analyse approved issues
- Create feature branches
- Generate code
- Generate tests
- Draft documentation
- Review pull-request diffs
- Suggest improvements
- Run approved development commands

AI agents may not:

- Push directly to `main`
- Merge their own pull requests
- Change branch protection
- Change governance documents without approval
- Change licences without approval
- Publish releases
- Publish model weights
- Add training data without review
- Access production systems
- Access unrestricted secrets
- Claim ownership or authorship on behalf of Southern
- Represent upstream work as original Southern work

All AI-generated code must undergo human and automated review.

## 8. Independent review

Where practical, implementation and review should use different systems.

Example:

1. Kimi creates an implementation.
2. Qwen creates or reviews tests.
3. DeepSeek reviews architecture and failure modes.
4. Automated security tools inspect the change.
5. An authorised human approves the pull request.

AI consensus is not a substitute for factual verification or human approval.

## 9. Initial technology standards

Preferred technologies for initial Southern services:

### Backend

- Python 3.12 or later
- FastAPI
- Pydantic
- SQLAlchemy where relational persistence is required

### Frontend

- TypeScript
- React
- Next.js

### Data

- PostgreSQL
- Redis where caching or queues are justified
- JSON Schema for portable data contracts

### AI and model serving

- PyTorch
- Hugging Face-compatible formats where appropriate
- vLLM or another approved inference engine
- OpenAI-compatible API interfaces where useful
- Provider-neutral model adapters

### Infrastructure

- Docker
- Docker Compose for local development
- Kubernetes only when scale justifies it
- Terraform for reviewed infrastructure-as-code

A technology outside these standards requires an Architecture Decision Record.

## 10. Coding requirements

Code must:

- Use type annotations where supported
- Validate external inputs
- Handle errors explicitly
- Avoid hard-coded credentials
- Avoid unnecessary dependencies
- Include useful documentation
- Be structured for testing
- Follow language-specific formatters and linters
- Avoid vendor lock-in unless explicitly approved

Python projects should initially use:

- Ruff
- mypy
- pytest
- Bandit where appropriate

TypeScript projects should initially use:

- TypeScript strict mode
- ESLint
- Prettier
- Vitest or Jest
- Playwright for browser workflows

## 11. Testing requirements

New functionality must include appropriate tests.

Testing layers may include:

- Unit tests
- Schema tests
- Integration tests
- API contract tests
- Security tests
- Model evaluation tests
- Regression tests
- End-to-end tests

Bug fixes should include a regression test where practical.

No benchmark result may be published without reproducible evaluation records.

## 12. Security requirements

Southern follows least-privilege access.

Prohibited:

- Secrets committed to Git
- Production credentials in developer environments
- Shared administrator accounts
- Unreviewed shell-install scripts
- Unpinned high-risk dependencies
- Direct AI-agent access to production
- Executing untrusted model output as code
- Sending protected data to external models without approval

Required security controls will include:

- Secret scanning
- Dependency scanning
- Static analysis
- Container scanning
- Code review
- Audit logging
- Environment isolation
- Credential rotation
- Responsible vulnerability disclosure

## 13. Data governance

Every dataset must document:

- Source
- Collector or creator
- Collection date
- Licence
- Permitted uses
- Provenance
- Personal-information assessment
- Cultural-sensitivity assessment
- Copyright assessment
- Review status
- Removal and correction process

Data found online is not automatically acceptable for model training.

## 14. Cultural and language materials

Southern is dedicated to elders and the preservation of languages, knowledge and heritage.

This dedication does not grant Southern authority over cultural material.

Indigenous language, cultural knowledge, stories, art and traditional knowledge must not be added to datasets merely because they are publicly accessible.

Such work requires appropriate:

- Community engagement
- Authority
- Consent
- Provenance
- Governance
- Attribution
- Access controls
- Benefit sharing where applicable

Southern must not imply endorsement by a community without documented permission.

## 15. Model requirements

Every supported or released model must have a model record containing:

- Model name and version
- Publisher
- Base model
- Model architecture
- Licence
- Upstream notices
- Commercial-use rights
- Redistribution rights
- Derivative-model obligations
- Training or adaptation method
- Evaluation results
- Safety limitations
- Compute requirements
- Data-handling implications
- Known weaknesses

A model adapted from an upstream model may use Southern branding only while preserving all legally required attribution and disclosures.

## 16. Reproducibility

Research and benchmark results should include:

- Source revision
- Environment details
- Model version
- Dataset version
- Configuration
- Random seed where applicable
- Hardware information
- Evaluation procedure
- Raw or auditable result records

Claims must be supported by evidence that others can inspect.

## 17. Architecture decisions

Important technical decisions must be recorded using Architecture Decision Records.

An ADR is required when:

- Selecting a core framework
- Introducing a significant dependency
- Selecting model-serving infrastructure
- Changing database architecture
- Introducing a cloud provider dependency
- Changing authentication
- Changing data formats
- Making a major security decision

ADR files must use:

`docs/adr/ADR-NNN-title.md`

## 18. Releases

Southern will use semantic versioning where applicable:

`MAJOR.MINOR.PATCH`

Every release should include:

- Version
- Date
- Change summary
- Security notes
- Upgrade notes
- Known limitations
- Licence notices
- Reproducible build information where possible

Only authorised maintainers may publish releases.

## 19. Definition of done

Work is complete only when:

- Requirements are met
- Tests pass
- Security checks pass
- Documentation is updated
- Licence and provenance are reviewed
- Relevant risks are documented
- Pull-request discussions are resolved
- An authorised maintainer approves the change

Code generation alone does not mean a task is complete.

## 20. Amendment

Changes to this standard must be proposed through a pull request and include:

- Reason for the change
- Operational impact
- Security impact
- Governance impact
- Migration requirements

During founding governance, amendments require approval from the founder.
